My first two tools were Python. This one is Go, and that choice is the whole
point. `gofuzz` is a web content discovery tool: give it a URL and a wordlist,
and it finds the paths that exist on a server by making many requests at once.
It's a stripped-down `ffuf` or `gobuster`, and I built it to understand the one
thing that makes those tools fast: concurrency.

You can read about goroutines and channels all day. Implementing the pattern
yourself is what makes it stick. This post is about the decisions behind that.

## Why Go for this, specifically

Directory discovery is a firehose of independent requests: try thousands of
paths, see which come back with something other than 404. That's an
embarrassingly parallel problem, and it's exactly what Go's concurrency model is
built for. Two things sold me:

**Cross-compilation.** One `go build` produces a single static binary with no
dependencies, and I can build for any OS from my machine:

```bash
GOOS=windows GOARCH=amd64 go build -o gofuzz.exe .
GOOS=darwin  GOARCH=arm64 go build -o gofuzz .   # Apple Silicon
```

No interpreter to install on the target, nothing to `pip install`. That's a real
operational advantage over a Python script.

**Goroutines.** Firing hundreds of concurrent requests in Python means wrestling
with threads or asyncio. In Go it's the natural way to write the program.

## Decision 1: the fan-out / fan-in pipeline

The core is a classic Go shape, and getting it right is the point of the whole
project:

- A **jobs channel** feeds paths to a pool of **worker goroutines**. This is the
  fan-out: instead of one loop doing requests one at a time, N workers pull work
  in parallel.
- Workers send their hits to a **results channel**, which a single goroutine
  drains and prints. This is the fan-in: all the parallel work funnels back into
  one place.

```go
jobs := make(chan string, cfg.workers)
results := make(chan result, cfg.workers)

for i := 0; i < cfg.workers; i++ {
    go worker(&wg, cfg, client, ticker, jobs, results)
}
```

The beauty of this shape is what it *avoids*: there's no shared list that every
worker writes to, so there are no locks and no race conditions. Each worker owns
its own work and communicates by sending on a channel. That's the Go philosophy,
"don't communicate by sharing memory; share memory by communicating," and
building it myself is what finally made that slogan concrete.

## Decision 2: closing channels in the right order

This is the part that trips everyone up, and getting it wrong gives you either a
deadlock or a panic. The sequence matters:

```go
for _, t := range tasks {
    jobs <- t
}
close(jobs)     // tell workers no more work is coming

wg.Wait()       // wait for every worker to finish
close(results)  // ONLY now is it safe: no worker will send again
<-done          // wait for the printer to drain the last results
```

You close `jobs` so the workers' `range` loops end. You wait on the
`WaitGroup` so you know every worker has returned. Only *then* can you close
`results`, because closing a channel a goroutine might still send on is a panic.
Reasoning through that ordering, rather than copying it, is where the real
learning happened.

## Decision 3: one rate limiter for the whole pool

A fuzzer that fires as fast as it can will knock over a small target or get you
blocked. So there's a rate limiter, and the subtle part is that it's *shared*:

```go
ticker = time.NewTicker(time.Second / time.Duration(cfg.rateLimit))
// ...in each worker:
<-ticker.C   // block until the limiter allows the next request
```

Because all workers read from the same ticker, `-r 50` means 50 requests per
second *in total*, not 50 per worker. I verified this: 200 requests at `-r 50`
took almost exactly 4 seconds. That's the difference between a tool you can point
at a real target and one that's a liability.

## Decision 4: don't follow redirects, don't download bodies

Two small choices that show the tool was built with intent:

I tell the HTTP client *not* to follow redirects. A 301 is itself a signal, the
path exists and points somewhere, so I want to see it, not silently chase it.

And workers read the status and content length, then close the body without
downloading it. When you're making thousands of requests, pulling down every
response body is wasted bandwidth. You only need the headers to know a path
exists.

## Takeaway

`gofuzz` is a tool I actually use, but the reason I built it was to internalise
Go's concurrency model by implementing it, not reading about it. Fan-out to a
worker pool, fan-in through a results channel, a shared rate limiter, and careful
channel-closing order: those four ideas are the foundation of almost every
concurrent Go program. Building a real tool around them beats any tutorial.
